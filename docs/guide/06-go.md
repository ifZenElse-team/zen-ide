# Go

GoGarden reads Go with gopls, the Go language server: completion and errors as you type,
navigation to declarations, implementations and usages, and the documentation of what you use.

Everything on this page is the **Go** plug-in, built into every Zen IDE and on in GoGarden. In
another Zen IDE, such as RustRonin, switch it on in **Settings → Plugins → Built-in** and restart
the IDE ([Built-in plug-ins](10-plugins.md#built-in-plug-ins)).

**File → New → Project…** creates a Go module ([New Go modules](#new-go-modules) below).

## New Go modules

The **Go** type comes first in [New Project](05-project.md#new-project). Its fields:

- **GOROOT**: the Go SDKs found (the one in use first) and **Local…**, which asks for an SDK's
  folder. Create stays disabled without an SDK, or when the folder has no `bin/go`, and the line
  above the buttons says why.
- **Module path**: the project's name until you change it.
- **Environment**: Go variables such as `GOPROXY=https://proxy.golang.org`, separated by `;`. They
  are saved with the new project in `.zen/go.json`, shared with everyone who has it, and used by
  `go mod init` and everything after ([The project's Go environment](#the-projects-go-environment)).
- **Add sample code** writes a `main.go` that prints a greeting.

**Create** runs `go mod init <module path>` in the new folder with the chosen SDK and
`GOTOOLCHAIN=local`, so it never downloads another toolchain. The project opens trusted when you
press Create; one an agent creates opens untrusted. Projects in GOPATH mode are not offered.

## Go and gopls

GoGarden finds the Go SDKs on your computer: in `GOROOT`, on `PATH`, from Homebrew, in
`/usr/local/go`, in `~/sdk`, and the toolchains `go` downloads itself. It finds gopls in `GOBIN`,
in `GOPATH/bin` (`~/go/bin` by default) and on `PATH`.

Adding, removing or choosing a Go SDK, gopls or Delve is yours alone: an agent gets `agentNotAllowed`,
before anything in the folder is started. It can still read the list and run the `toolchain.*.install`
commands.

An SDK is kept by the path that stays the same across upgrades: Homebrew's Go is
`/opt/homebrew/opt/go/libexec` (or `/usr/local/opt/go/libexec`), not the
`/opt/homebrew/Cellar/go/1.27.2/libexec` folder it leads to today, which `brew upgrade go` removes.
A `go` on `PATH` that is only a launcher (an asdf, mise or goenv shim) is asked for its `GOROOT`.

- **Upgrading Go while GoGarden runs** needs no restart: within a few seconds GoGarden notices the
  new version (read from the SDK's `VERSION` file), shows it in **Settings → Go**, restarts gopls
  with it, reloads the project's modules and libraries, and runs, tests and go.mod checks use it.
- **A chosen SDK whose folder is gone** (an upgrade removed it, or you deleted it) is shown in red
  under **GOROOT**; GoGarden meanwhile uses the SDK now at the same stable path, or the first one
  found, and **Use go1.27.3 …** makes that the choice in one click. A choice that an older GoGarden
  saved as a Homebrew `Cellar` folder is changed to the stable path by itself.

- **Settings → Languages & Frameworks → Go** shows the SDK in use (GOROOT), lets you choose another
  one found, and shows gopls and its version, with **Install gopls** or **Update gopls**; see
  [Go settings](#go-settings) below.
- When gopls is missing, a notification above a Go file offers **Install**: it runs
  `go install golang.org/x/tools/gopls@latest` with the SDK in use and shows how it goes. Without Go
  at all, it says so and links to [go.dev/dl](https://go.dev/dl/) (**Download Go**).
- gopls is one of the IDE's [language servers](language-servers.html): the status bar shows whether
  it runs, and from there you restart or stop it, read its log, or start another gopls program with
  other arguments.

## Go settings

**Settings → Languages & Frameworks → Go** has four parts. Changes to the SDK, gopls and Delve apply
at once, without **OK**, in every window: gopls restarts with them, and the project's modules and
libraries and the next run, test or debug session use the new SDK and Delve.

- **GOROOT**: the SDK in use, chosen from those found. **Add SDK → Local…** adds an SDK GoGarden did
  not find: choose its folder, the one that holds `bin/go`. GoGarden reads its version from its
  `VERSION` file, or asks `go version`; a folder without a working `go` is refused with the reason
  under the list. An SDK you added is remembered and listed with the others, and **Remove** takes it
  off the list again (only SDKs you added can be removed).
- **gopls**: the gopls in use, its version and its path. **Custom path** uses another gopls: type
  its path or pick the file with **Browse…**; GoGarden checks that it answers `gopls version` before
  using it. Empty the field to go back to the gopls found. **Install gopls** or **Update gopls** runs
  `go install golang.org/x/tools/gopls@latest`, only when you click it; **Look again** searches for
  SDKs and gopls once more.
- **Delve**: the Go debugger (`dlv`) that debugging starts, its version and its path, or **Not
  found**. GoGarden finds it where it finds gopls: in `GOBIN`, in `GOPATH/bin`, on `PATH`, then in
  `/opt/homebrew/bin` and `/usr/local/bin`. Delve older than 1.20 is marked as too old to debug
  with. **Custom path** uses another `dlv`, once it answers `dlv version`; empty the field to go
  back to the one found. **Install Delve** or **Update Delve** downloads the latest Delve with
  `go install github.com/go-delve/delve/cmd/dlv@latest` into `GOPATH/bin`, only when you click it;
  nothing is downloaded otherwise.
- **On Save**: **Reformat code on save** and **Optimize imports on save** are the options of
  **Tools → Actions on Save**, shown here too; **Configure on Actions on Save** opens that page.

Your choices are kept in `toolchain.json` in GoGarden's data folder: the SDK in use (`goSdk`), the
SDKs you added (`customSdks`), the gopls path you chose (`goplsPath`) and the Delve path you chose
(`dlvPath`).

## The project's Go environment

**Settings → Languages & Frameworks → Go → Go Modules** sets Go variables for the open project,
such as `GOPROXY=https://proxy.corp.example; GOPRIVATE=*.corp.example; GOFLAGS=-tags=integration`,
separated by `;`. They reach every `go` command GoGarden runs for the project (runs, tests,
coverage, debugging, the go.mod checks and updates, `go vet` and staticcheck, installing gopls and
Delve) and gopls, which restarts when you change them.

- **Shared with the project (.zen/go.json)**: kept in the project, so everyone who clones it gets
  them. Never put a password or token here: a URL with a user name or password is refused, and so
  are `GOENV` and `GOTOOLCHAIN`. They apply only once you trust the project; until then the page says
  so, and the trust notification names `.zen/go.json`.
- **Only on this computer**: kept in GoGarden's data folder for this project. Your values win over
  the shared ones; this is the place for a proxy URL with a token, or another `GOTOOLCHAIN`.
- **In effect** lists every variable with where it comes from. A run configuration's own
  environment wins over both layers, and both win over your login shell's. The IDE's own checks still run with
  `GOTOOLCHAIN=local` and `GOPROXY=off`, and add `-mod=readonly` after your `GOFLAGS`.

Only names that start with `GO` or `CGO_` are taken; `GOROOT` is the SDK chosen above, and `PATH`
belongs in a run configuration. Agents read the environment with `go.env.get` (a user name or
password in a URL is shown as `***`); only you change it (`go.env.set`), because it can run code.

## Colours

Besides the colours every Go file gets (keywords, strings, comments, numbers, calls), gopls tells
GoGarden what each name is: package names are olive, types teal, calls of functions and methods
sand-coloured (their declarations stay blue), constants purple and italic wherever they are used,
in other files and packages too (`model.MaxItems`), and built-in types such as `error` look like
keywords. They appear a moment after a file opens and follow your
edits.

## Inlay hints

gopls gives the [inlay hints](02-editor.md#inlay-hints): parameter names before the arguments of a
call (`greet(name: "Ann")`), field names in composite literals (`Point{X: 1}`), the types of
variables and of composite literals declared without one, the type arguments inferred for a call of
a generic function and the values of constants. Only parameter names are on at first;
[Settings → Editor → Inlay Hints](09-settings.md#editor--inlay-hints) switches each kind,
and gopls is told at once, without a restart.

## Completion

As you type a name or a `.`, a list of what fits there opens under the caret; **⌃Space** opens it
at any time. Each item has its kind (function, variable, field, type, package...), and on the right
its type or signature; the letters you typed are bold, and the list narrows as you go on typing.
The selected item's documentation shows in a panel beside the list, to its right, or to its left
when the window has no room on the right.

- **↑** and **↓** choose; **Enter** inserts the item, **Tab** replaces the rest of the word after
  the caret; **Escape** closes the list. A click inserts too.
- A function comes with its parentheses, the caret between them. When the call already has its
  arguments (choosing `Total` at `item.|Total(2)`), only the name changes and the arguments stay:
  `item.Total(2)`, with Enter and with Tab. A generic function (`Map[T any](xs []T)`) goes in as
  its name only too: `Map(xs)`.
- An item from a package the file does not import yet (shown as `from "strings"`) adds the import.

## New Go files

**New → Go File** (**⌘N** in the Project tool window, or File → New) asks for the name and the
**Kind**: **Go File**, with only the package clause, or **Simple Application**, `package main` with
`func main()`. The file opens with the caret after the package clause or inside `main`.
**New → Go Test File** adds `_test` to the name and starts with the package and `_test`.

Both are in the list only in a folder of a Go module or workspace (`go.mod` or `go.work` there or
above it) or one with Go files. You can change them in **Settings → Editor → File and Code
Templates**, where `${GO_PACKAGE_NAME}` is the package of the Go files beside the new one, or the
folder's name when there are none, and `${GO_PACKAGE_NAME_WITH_TEST_SUFFIX}` is that name with
`_test`.

## Live templates

Type an abbreviation and press **Tab** ([Live templates](02-editor.md#live-templates)); the
variables to fill in are in capitals:

| Abbreviation | Becomes |
|---|---|
| `for` | `for CONDITION { }` |
| `fori` | `for i := 0; i < n; i++ { }` |
| `forr` | `for _, item := range COLLECTION { }` |
| `if`, `ifelse` | `if CONDITION { }`, with `else { }` |
| `iferr` | `if err != nil { return err }` |
| `func`, `meth` | a function; a method with a pointer receiver |
| `main`, `test`, `bench` | `func main()`, `func TestNAME(t *testing.T)`, `func BenchmarkNAME(b *testing.B)` with a `b.Loop()` loop |
| `struct`, `interface` | `type NAME struct { }`, `type NAME interface { }` |
| `switch`, `select` | a `switch` with one `case`, a `select` with one `case` |
| `go`, `defer` | `go func() { }()`, `defer func() { }()` |
| `print`, `printf` | `fmt.Println(VALUE)`, `fmt.Printf("%v\n", ARGUMENTS)` |

`print` and `printf` add the `fmt` import when the file does not have it, `test` and `bench` add
`testing`: into the `import ( ... )` block in order, turning a single import into a block, or after
the package clause.

Change them, switch them off or add your own in Settings → Editor → Live Templates.

After an expression and a dot, [postfix templates](02-editor.md#postfix-completion) wrap it:
`ok.if`, `ok.else`, `err.nn`, `p.nil`, `items.for`, `n.fori`, `x.var`, `x.not`, `x.switch`,
`x.return`, `x.print` (adds `fmt`), `x.par`, `s.len`. **⇧⌘⏎**
([Complete Current Statement](02-editor.md#complete-current-statement)) closes the brackets and
adds the block of an `if`, `for`, `switch`, `select`, `func`, `struct` or `interface`; `//` typed
above a declaration starts its documentation comment with its name.

**⌥⌘T** ([Surround With](02-editor.md#surround-with)) wraps the selection or the statement at the
caret in `if`, `if / else`, `for` or `func() { … }()`, a selection also in `(…)` or `!(…)`, or in
a `// region` or `// <editor-fold>` comment pair.

## Navigation

GoGarden asks gopls where things are:

- **⌘B** (Navigate → Declaration or Usages), or **⌘-click** on a name, goes to where the name is
  declared. Holding **⌘** over a name that leads somewhere turns it into a blue, underlined link
  and the pointer into a hand (names without a declaration, such as keywords, stay as they are); resting there a moment shows the name's declaration above it, highlighted (for example
  `func TestLegacyKey(t *testing.T)`).
  When a name has several declarations, a list titled "Choose Declaration" opens at the caret.
  On the declaration itself, **⌘B** lists the name's usages instead, or goes to the only one.
- **⌥⌘B** (Navigate → Implementation(s)) goes to the implementations of an interface or its
  method: straight there when there is one, or a list "Implementations of … (n)".
- **⇧⌘B** (Navigate → Type Declaration; also **⌃⇧B**), or **⇧⌘-click** on a name, goes to the
  declaration of its type: on a variable `f := &File{}` it opens `type File struct`. gopls takes
  the named type under `*`, `[]`, `map` and `chan`; several types open "Choose Type Declaration".
- **⌘U** (Navigate → Super Method) anywhere in a method of a concrete type, on its name or in its
  body, goes to the interface method it implements, for example from
  `func (f *File) Read(p []byte) (int, error)` to `Read` in `io.Reader`; when it implements several,
  a list "Super methods of … (n)" opens. It only goes up: a method of an interface, a
  function, or a method that implements no interface says "The method has no super method" (**⌥⌘B** goes
  down, to the implementations).
- **⇧⌘T** (Navigate → Test) goes from a function or method to its tests (`TestTotal`,
  `TestCart_Total`, benchmarks, examples and fuzz tests) and back, or between `cart.go` and
  `cart_test.go`; with no test it offers Create New Test…, which writes a table-driven test
  ([Go to Test and Create Test](15-run-and-test.md#go-to-test-and-create-test)).
- In a list, each row shows the file's icon, the line with the name in bold, and the file and line
  number; **↑** and **↓** choose, **Enter** or a click goes there, **Escape** closes it.
- When there is nothing to go to, a notice says so ("Nothing to go to: the declaration is not found", "Nothing
  to go to: the type declaration is not found", "The method has no super method"). If you
  move the caret or type before gopls answers, the answer is dropped.
- Every jump is remembered, so **⌘[** (Back) returns to where you were
  ([Back and Forward](03-navigation.md#back-and-forward)).

## Find Usages

Put the caret on a name and press **⌥F7** (or **Edit → Find Usages → Find Usages**): gopls looks
for every place the name is used, and the **Find** tool window opens at the bottom with a tab
**Usages of** the name and how many usages there are in how many files. While gopls looks, the
status bar shows **Finding usages of '…'**.

The tab works like the tab of [Find in Files](04-find-and-replace.md#the-find-tool-window):

- The tree starts with **Targets** (what was looked for, such as **Variable Version**) and
  **Usages in Project Files** with the usages under it. The declaration itself is not listed.
- **Group By** groups the usages as for text: **Usage Type** (**⌃T**), **Module** (**⌃M**),
  **Directory Structure** (**⌃D**), **Group by Directory** (**⌃P**), **File Structure**
  (**⌃S**), **Flatten Modules** (**⌃O**), **Production/Test**, and **Merge Usages from the Same
  Line** (**⌃L**), which lists the usages of one line as one row with each of them in bold.
- With Usage Type, the usages that read the name are under **Value read** and those that change it
  under **Value write**, as gopls tells it. **Show Read Access** and **Show Write Access** in the
  toolbar hide or show them; a usage gopls does not classify stays under **Unclassified** and is
  always shown. Usages in imports and comments have groups of their own.
- **Preview Source** shows the code around the selected usage on the right.
- **Rerun** (**⌘R**) asks gopls again; **Pin Tab** keeps the tab, so the next Find Usages opens a
  new one; **Open results in new tab** makes every Find Usages open a new tab. **⌥⌘↑** and
  **⌥⌘↓** go to the previous and next usage; **⌫** excludes a usage (struck through).
- Click a usage to go to it, or choose it with **↑** and **↓** and press **Enter**, which also puts
  the keyboard back in the editor. **←** and **→** collapse and expand a node; **Escape** returns
  to the editor.
- When there is nothing, the tab says **No usages found in Project Files**.
- **⌘3**, or the Find button on the left, shows and hides the window; it shares the bottom of the
  window with the Terminal and Problems.

**Edit → Find Usages → Find Usages Settings…** (**⌥⇧⌘F7**, also **Settings** in the tab's
toolbar) opens the **Find Usages** dialog for the name at the caret: the **Scope** (**Project
Files**, **All Places**, **Open Files**, **Current File**), **Open in new tab**, and **Skip results
tab with one usage**, which opens a single usage in the editor instead of a tab. **Find** keeps the
choices for the next Find Usages and looks; **Cancel** keeps nothing.

**Edit → Find Usages → Recent Find Usages** lists the Find Usages done in the window, newest first,
with the file and the scope; **Enter** or a click runs one again (if the file changed since, the
name is looked for on the line it was on, else near where it was). **Rerun** finds it the same way.

## Show Usages

Press **⌥⌘F7** (or **Edit → Find Usages → Show Usages**) to see the usages of the name at the caret in a
popup right there, without leaving the editor. Clicking the **N usages** row of
[Code Vision](02-editor.md#code-vision) opens the same popup under the row.

- The header says what the name is, where it is declared and how many usages it has:
  **Variable Version in cmd/main.go · 3 usages**. **Open in Find Tool Window** (**⌥F7**) moves the
  list, in the popup's scope, to a tab of the [Find tool window](#find-usages).
- Each row shows the file, its module in grey, the line number, whether the usage reads or writes
  the name (an eye or a pencil), and the line with the usage in bold. The bottom of the popup shows
  the path of the selected row. The declaration itself is not listed.
- The first 100 rows are listed; the last row, **N more usages**, lists the next 100.
- **↑** and **↓** choose a row, **Enter** or a click goes to it, **Escape** or a click outside closes
  the popup. Drag the header to move the popup.
- The toolbar: **Merge Usages from the Same Line** (**⌃L**), **Show Read Access** (**⌃R**),
  **Show Write Access** (**⌃W**), **Show Results In Generated Code** (files marked
  `Code generated … DO NOT EDIT.`), **Show Import Statements** (**⌃I**), **Show Usages In Comments**
  (the name in `//` and `/* */` comments), **Show Options** (all the toggles in one menu),
  **Preview Source** (the lines around the selected usage under the list), the scope and
  **Settings** (**⌥⇧⌘F7**, the Find Usages dialog; its **Find** shows the popup again in the
  scope chosen). While the
  popup is open, **⌃R** is Show Read Access, not Run.
- The scope is **Project Files** at first. Press **⌥⌘F7** again while the popup is open to widen
  it: Current File → Open Files → Project Files → All Places (files outside the project too).
- Whether a usage reads or writes comes from gopls's usage highlighting where the editor has it,
  and otherwise from the text (an assignment, `:=`, `+=`, `++` after the name).

## Call and type hierarchy

GoGarden asks gopls who calls a function and what it calls, and how types and interfaces relate.
Put the caret on a function, method or type and
choose **Navigate → Call Hierarchy** (**⌃⌥H**; Ctrl+Alt+H on Windows and Linux) or **Navigate →
Type Hierarchy** (**⌃H**; Ctrl+H). The **Hierarchy** tool window opens on the right with the tree;
**View → Tool Windows → Hierarchy** shows it again (it has no shortcut).

- **Call hierarchy** of the function or method at the caret: its **callers**, or its **callees**.
  Each caller comes with the lines where it makes the call (a node calling more than once says how
  many times).
- **Type hierarchy** of the type at the caret: for an interface, the types that implement it
  (**subtypes**); for any other type, the interfaces it implements (**supertypes**).
- The first level comes at once; a node's next level is asked for only when you expand it (click
  its arrow, or **→**), so a large project costs nothing until you look deeper. A recursive call is
  marked with a circular arrow and never expanded, so the tree always ends.
- **Double-click**, **⏎** or **F4** on a node opens its code; **⌘[** (Back) returns to where you
  were. With **Navigate with Single Click** on, one click does it. **←** and **→** collapse and
  expand, **⎋** returns to the editor.
- Nodes in test files (`_test.go`) are tinted green, as test files are in the Project tool window;
  library and SDK nodes are greyed.

The toolbar, left to right:

| Button | What it does |
|---|---|
| **Caller Hierarchy** / **Callee Hierarchy** (types: **Supertypes** / **Subtypes Hierarchy**) | which way the tree goes from its root |
| **Sort Alphabetically** | sorts each node's children by name instead of as gopls lists them |
| **Scope** | **Project** (the project without tests), **Test** (only its test files) or **All** (with the libraries and the Go SDK); the node you started on is always shown |
| **Refresh** | builds the hierarchy again after edits, with the nodes you had expanded expanded again |
| **Navigate with Single Click** | one click on a node opens its code |
| **Expand All** / **Collapse All** | expands every node three levels deep (in a very wide tree, the first 256 nodes; open the others by hand), or collapses the tree to its root |
| **Pin Tab** | keeps the tab: the next hierarchy opens in another tab |
| **Close** | closes the tab |

Every hierarchy is a tab titled by what it shows ("Callers of Total", "Subtypes of Store"). A new
hierarchy replaces the tab you are on unless it is pinned; pinned tabs stay and keep working
(expand, refresh, change direction). Click a tab's title to switch to it. The scope, sorting and
single-click choice are kept for the next hierarchy and remembered with the project.

gopls does not list calls made through an interface or a function value, and builds a type
hierarchy only from v0.19 on, for named types. A gopls without it, or another language server
without call or type hierarchy, is reported in the tool window ("gopls does not provide a type
hierarchy") instead of an error. AI agents use the same tabs through the `navigate.hierarchy.*`
commands ([AI agents](ai-agents.html)). The same works with any language server that provides the
hierarchies.

## Quick documentation and parameter info

**F1** (or **⌃J**) shows the documentation of the name at the caret in a popup under it: its
declaration first, then what gopls has to say about it, with code, lists and links. Press **F1**
again and the popup stays; **Escape** or moving the caret closes it. A link opens in your browser
only when you click it.

**⌘P** inside a call shows the parameters of the function above the caret: the one the caret is in
is bold. As you move through the arguments the bold one follows, and the popup closes when the caret
leaves the call or on **Escape**. A function without parameters shows `<no parameters>`; when a
call fits several signatures, each has its own line.

Both are in **View** in the main menu too.

## Rename

In the editor, **⇧F6** (or **Refactor → Rename…**) renames the name at the caret (a variable, function, type,
field, method...) everywhere in the project, as gopls finds it. The **Rename** dialog opens with the
current name selected: type the new one and press **Enter** (or **Refactor**) to rename at once, or
**Escape** (or **Cancel**) to leave it. If there is nothing to rename at the caret, GoGarden says so
instead of opening the dialog; a new name that cannot be used is shown in red under the field.

**Preview** shows every change before anything is changed: the **Find** tool window opens on a
**Refactoring Preview** tab with the usages, file by file, each line with its number, the old name
struck through and the new one in bold. Click a line to go there. **Do Refactor** makes the changes;
**Cancel** closes the tab and changes nothing.

- The new name must be a Go identifier: a letter or `_`, then letters, digits and `_`, and not a
  keyword.
- Every file changes, or none does: if a file was edited after the changes were computed, or one
  cannot be written, nothing is changed and GoGarden says why; try again.
- Open files get the change without being saved; files that are not open are written at once.
- **⌘Z** in a file the rename changed undoes the whole rename, in every file. A file you changed
  after the rename is left as it is, and GoGarden names it.
- A rename may also create, rename or delete files, as the language server decides (renaming a Java
  class renames its file, renaming a Rust module moves its file). The preview lists them under
  **Files to create, rename or delete**; such files must be inside the project, else nothing is
  changed. One **⌘Z** brings back the files too, a deleted one included.
- Renaming in place in the editor, without the dialog, comes later.

## Quick fixes and intentions

**⌥⏎** at the caret lists what gopls offers there: quick fixes for the problem under the caret or on
its line (add a missing import, create an undeclared variable...), then refactorings
such as extracting a function or a variable, inlining a call and filling a struct, and source
actions such as organising imports. A bulb in the gutter of the caret line shows that there are
some (red when one fixes a problem); click it or press ⌥⏎, choose with the arrows and press
**Enter**. Some actions are commands that gopls runs itself, sending the changes back; GoGarden
applies those as one step too, for **⌘Z**, and refuses any change gopls sends when no action asked
for it. See [the editor's page](02-editor.md#context-actions).

## Generate

**⌘N** (Code → Generate…, [the editor's page](02-editor.md#generate)) offers, with the caret inside
a struct type, **Constructor…**: choose the fields to initialize and whether it returns a pointer,
and GoGarden writes `NewPoint(x int, y int) *Point` (`newPoint` for an unexported type, with the
type's parameters for a generic one) after the type, in gofmt's layout. On a function, gopls'
**Add test for …** writes a table-driven test into the package's `_test.go` file (while that file
does not exist yet, gopls has to create it, which is refused for now, with a message saying so).

**Getter…**, **Setter…** and **Getter and Setter…** are offered inside a struct type too: choose the
fields and each gets its methods after the type, with a pointer receiver. A field `name` gets
`Name()` and `SetName(name string)`; an exported field `Age` gets `GetAge()` and `SetAge(age int)`,
because a method cannot share its field's name. A field that has its methods already is not listed.

**Implement Methods…** (**⌃I**, or in the Generate list) works inside a type or on one of its
methods. Type to search the interfaces of the project's module and the standard library, by name or
package, and press **Enter**: the type gets a stub with `panic("implement me")` for every method it
does not have yet, embedded interfaces included, and the imports the signatures need. Generic
interfaces are not listed, nor are interfaces of the module's dependencies or those that embed them.

## Struct tags

Inside the backticks after a struct field, **⌃Space** completes what fits the place:

- **Keys:** `json`, `yaml`, `db`, `xml`, `toml`, `bson`, `mapstructure`, `form`, `validate` and `gorm`,
  without those the tag already has. Picking one writes `json:""` with the caret between the quotes.
- **Values:** the field's name as `user_id`, `userId`, `user-id` and `UserId`, and `-`.
- **Options,** after a comma: what the key has, such as `omitempty` for `json`.

**Generate** (**⌘N**) inside a struct offers **Struct Tags** once per case (`field_name`, `fieldName`,
`field-name`, `FieldName`). Choose the fields and the keys, and `omitempty` if you want it. Only
exported fields with a line of their own are listed. A key a field's tag already has keeps its
value, and the tags' column lines up.

**Reformat Code** lines up the values of tags on neighbouring fields, as long as their keys come in
the same order; a blank line or a field without a tag starts a new group. `gofmt` keeps the column of
the tags aligned and leaves their insides alone, so this is the step that does it. **Settings → Editor
→ Code Style → Go → Line up the values of struct tags** turns it off.

## go:generate and benchmarks

A `//go:generate` line has a run icon in the gutter. It runs `go generate` for that line alone, in
the file's folder inside its module, and shows the output in the Run tool window; the configuration
is a temporary **Go Generate**, which you can keep. With the caret on the line, ⌃⇧R runs it too. A
Go Generate configuration without a directive runs all the file's lines.

A benchmark runs from its gutter icon as any test, always with `-benchmem`. Above the console, the
Run tool window shows a table of the results: for each benchmark and sub-benchmark how many times it
ran and its `ns/op`, `B/op`, `allocs/op` and the metrics it reports itself.

Agents find both with `run.targets.list`, start them with `run.process.start` and read the table's
numbers from `run.tests.get`, in each test's `iterations` and `measures`.

## Templates and embedded files

Go templates (`*.tmpl`, `*.gotmpl`, `*.gohtml`) are highlighted: the `{{ }}` of actions, their
keywords, functions, `.Fields`, `$variables`, strings and comments, and the HTML around them when
the file holds HTML. The caret on a brace shows its pair, as in any file.

**⌘-click** (or **⌘B**, Go to Declaration) on a pattern of a `//go:embed` line opens the file, or
lists the files when it matches several, following Go's rules: a folder gives its files without
those starting with `.` or `_`, unless the pattern starts with `all:`. On `//go:embed` itself, it
takes all the line's patterns. Binary files are not listed. Agents use
`navigate.declaration.goTo`.

## Reformat and optimize imports

- **Code → Reformat Code** (**⌥⌘L**) formats the whole file as `gofmt` does, also when text is
  selected.
- **Code → Optimize Imports** (**⌃⌥O**) adds the imports the file needs, removes the unused ones
  and sorts them, as `goimports` does.

Both come from gopls, so nothing else needs installing, and each is one step for **⌘Z**. If you type
while gopls is still working, its answer is dropped and the file stays as you left it; if gopls is
not running, a message says so.

To do both every time you save, turn on **Reformat code** and **Optimize imports** in
**Settings → Tools → Actions on Save**. Saving waits at most a second for each; if gopls is not
running or does not answer in time, the file is saved as it is and a message says so.

## Debug

GoGarden debugs Go programs and tests with Delve, and every debugger feature works on Go code. Click
a line number to set a breakpoint, right-click it to give it a condition in Go such as `i == 3`, and
press **⌥F8** while the program is stopped to evaluate a Go expression in the selected frame. The
full guide is [Debugging](16-debugging.md).

## Problems

When a Go file is open, GoGarden starts gopls for the project and sends it every change as you
type, saved or not. What gopls finds shows up in a second or two:

- **Errors** are underlined with a red wavy line, **warnings** with an amber one, and **hints**
  (such as code that could be simpler) with a grey one.
- **Unused code** that gopls marks as unnecessary is greyed out in the theme's unused colour
  instead of underlined. An unused import or variable stops the build, so it keeps its red
  underline as well.
- Marks on the right edge of the editor show where the problems are in the file; the counts in the
  editor's top right corner say how many errors and warnings it has.
- Hover over an underline or a mark to read the message; click a mark to go there.
- **F2** and **⇧F2** go to the next and previous problem.

The **Problems** tool window (**⌘6**, **View → Tool Windows → Problems**, or its button on the left) lists the current file's problems,
or on **Project Errors** every file's. Click a problem to go to it. It shares the bottom of the
window with the Terminal and the Find tool window.

A `go.mod` or `go.work` that GoGarden cannot read for the project's modules (an unknown directive,
a `use` folder without a `go.mod`) is a problem too, open or not: it is listed on **Project
Errors** and its line is underlined in the editor until the file is fixed and saved (while you
edit, the mark moves with the lines). When gopls already reports an error on that line, it is
listed once. gopls is told when a `go.mod`, `go.sum`, `go.work` or Go file changes on disk, saved in
GoGarden or changed by another program, so its own problems follow too.

If gopls stops, GoGarden starts it again and says so; after three stops in three minutes it leaves
it stopped and tells you why.

## go vet and staticcheck

Beside gopls's problems, GoGarden checks the package of an open Go file with `go vet` and, when it is
installed, with `staticcheck`. Their problems are underlined in the editor and listed in the
**Problems** tool window with **go vet** or **staticcheck** as their source; style checks are weak
warnings. A problem gopls already reports on the same line is listed once.

- **When they run.** In the background when a file is opened and each time it is saved, never while
  you type, or at once with **Run go vet and staticcheck** in **Find Action**. An unsaved edit keeps
  the marks of the lines it did not touch; the others come back after the next save.
- **Quick-fixes.** Where `go vet` gives a fix (**Insert "%s" format string**), **⌥↵** lists it.
  `staticcheck` gives none in its output. A fix saves the file first and is refused when the file
  changed after the check.
- **Settings.** **Settings → Languages & Frameworks → Go → Inspections** turns each tool off, and
  **Check when a file is saved** off leaves only the action above.
- **staticcheck.** GoGarden uses the one in `GOBIN`, `GOPATH/bin` or on `PATH`. **Install staticcheck**
  on the same page downloads it with `go install honnef.co/go/tools/cmd/staticcheck@latest`, only when
  you click it.

Neither check uses the network: they run with `GOPROXY=off`, `GOTOOLCHAIN=local` and
`GOFLAGS=-mod=readonly`, so a package whose modules are not downloaded yet is simply not checked. They
run only in a trusted project, only for files of the project, and not in Power Save Mode.

## go.mod: colours, newer versions and vulnerabilities

`go.mod` is coloured this way: directives such as `module` and `require` are keywords, versions
and the Go release are teal, module paths are plain text, `// indirect` and comments are grey.

While a `go.mod` is open, GoGarden checks its requirements:

- **Newer versions.** It asks the Go module proxy of your toolchain (`GOPROXY`, by default
  `proxy.golang.org`) for each module's versions. An outdated version gets a quiet wavy underline;
  rest the pointer on it for **Newer version is available: v1.2.6** with **Update dependencies…**
  (**⌥⇧↵**) and **More actions…** (**⌥↵**). Pseudo-versions (`v0.0.0-2019…`) and `+incompatible`
  versions are updated to the newest release.
- **Deprecated modules.** The proxy also gives the `go.mod` of each module's latest version; when
  its author marked the module deprecated (a `// Deprecated:` comment), the module's path is struck
  out. Its popup says **Deprecated module github.com/hhrutter/lzw.** with the author's **Deprecation
  notice**, and **Show github.com/hhrutter/lzw deprecation notice** (**⌥⇧↵**) opens it whole.
- **Retracted versions.** A version the module's authors retracted (a `retract` directive in that
  same `go.mod`) is underlined as a warning with their reason, and the fix updates it to the newest
  version that is not retracted. Retracted versions are never offered as updates.
- **Excluded versions.** A version this `go.mod` excludes (`exclude`) is a warning, with an update
  to the next version that is not excluded; excluded versions are never offered either.
- **Newer major versions.** When a newer major version of a module you require directly exists
  (`github.com/go-chi/chi/v5` for `github.com/go-chi/chi`), its path gets the quietest hint,
  **Newer major version is available: github.com/go-chi/chi/v5 v5.5.0**, with a link to it. Moving
  to a major version changes import paths, so it has no quick-fix.
- **Known vulnerabilities.** It reads the Go vulnerability database (`vuln.go.dev`) and, for the
  score of each advisory, the OSV database (`osv.dev`). A module with known vulnerabilities is
  underlined across its line in the warning colour; rest the pointer on it for the list of
  advisories (each id links to its page, with its CVSS score and title), **Show details…** (every
  advisory with its ids, severity, fixed versions and description) and **Update to unaffected
  version v0.35.0** — the oldest version without the vulnerabilities that have a fix. The details
  end with where the data comes from: the Go vulnerability database's reports are licensed under
  CC BY 4.0. Every network call of these checks, and how to turn it off, is in the website's
  privacy page.
- **The Go version.** The `go` directive is compared with the stable Go releases (from
  `go.dev/dl`). An older one says **Newer Go version is available: 1.27.3** and its popup offers
  two fixes on the spot: **Update go directive to 1.27.3**, the newest release, and **Update to
  1.26.10**, the newest patch of the release the line already names. The first is left out when
  the newest release is on the line's own release (`go 1.27.0`), the second when the line already
  names that patch. A `toolchain` line gets the same two (**Update toolchain to go1.27.3**,
  **Update to go1.26.10**); they all run `go mod edit`. `go 1.26` means "at least Go 1.26", the
  language version, which Go orders before `1.26rc1` and `1.26.0`; it never means "the latest
  1.26.x", so its patch fix writes the full release, `go 1.26.10`. When the module needs a newer Go than
  the Go SDK the project uses, the `go` directive is a warning with **Configure Go SDK…**, which
  opens **Settings → Languages & Frameworks → Go**.
- **What `go` itself says.** In the background GoGarden runs `go list -m -json -e all` and `go mod
  tidy -diff` (Go 1.23 and later) with the project's Go SDK, changing nothing: a version `go`
  cannot find is an error on it, an indirect requirement nothing uses any more is greyed out
  (drawn in the theme's unused colour, not underlined; it is still a weak warning in the counts and
  the Problems tool window; gopls's own "is not used in this module" for it is not shown again, and
  a direct requirement gopls finds unused is greyed out the same way, without an underline),
  and a requirement `go.sum` lacks a line for is an error (every requirement needs its `go.mod` hash, and a
  direct one the hash of its files too, as `go build` does); each offers **Run go mod tidy**, which
  runs `go mod tidy` in the module's folder and restores the missing `go.sum` entries.
- **Changes on disk.** The marks follow `go.mod`, `go.sum` and `go.work` as they are on disk: after
  a `git reset`, a checkout or an edit in another program they match the files at once, never what
  was there before.
- The counts in the editor's top right corner include them: errors, warnings, and the quieter weak
  warnings. The **Problems** tool window lists them too.

A popup opens only while the pointer rests on what is underlined (or struck out, or greyed out) itself, never on
the rest of the line or on empty space, after the same short delay every time, and it closes when
the pointer leaves (you can move the pointer into it to click its links). When several problems
share the spot, such as **Missing go.sum entry** and **Newer version is available: v0.22.0**, the
popup shows them all with the fix of each: **Run go mod tidy** (**⌥⇧↵**) and **Update to v0.22.0**,
and **More actions…** lists every fix of all of them.

**⌥↵** (**Show Context Actions**) on a requirement's line lists its quick-fixes; **⌥⇧↵** applies the
first one at once. **Update dependencies…** opens a dialog with every outdated module of the file,
one row each (`module: v1.0.0 → v1.2.6`), all checked; **Select All** and **Select None** check or
uncheck them all, a long list scrolls, and **Update (3)** says how many it updates. **Update to v…
and run go mod tidy** also tidies the module afterwards.

An update never stops the window: it saves `go.mod` and runs `go get module@version…` (and `go mod
tidy` or `go mod edit`) with the project's Go SDK in the module's folder, in the background. The
**background tasks** panel opens at the bottom right at once with what `go` prints as it prints it;
**Hide** hides it, and the task's title and progress bar in the status bar show it again. When `go`
is done, the panel says it finished, `go.mod` and `go.sum` are read again and the checks run again,
even when `go` changed nothing. When it fails, the panel shows `go`'s error and an error notification says
so too.

`go` raises your `go` line to the highest one an updated module's own `go.mod` names: after an
update `go 1.26` can become `go 1.26.0`. When an update (**Update to v…**, **Update
dependencies…**, **Run go mod tidy**) does that, the task's log and a notification say so, from what
to what and why: **The go directive was raised from 1.26 to 1.26.0: github.com/gofiber/fiber/v3
v3.6.1 and 6 more require go 1.26.0** (the first module that requires it, then how many more).

`go.work` files are checked too: their `go` and `toolchain` directives as above, and every `use`
folder that does not exist or has no `go.mod` is an error.

### Completing versions and going to a module

Inside a `go.mod` or `go.work`, **⌃Space** after a module's path, in `require`, `exclude` or on the
right of `replace`, lists its versions, newest first, with the newest release marked **Latest**.
Retracted versions and the ones this `go.mod` excludes are left out. The list comes from the answers
the checks above already have: completing contacts nothing, so with **Check for newer versions of
dependencies** off, or for a module the proxy has not been asked about, nothing is listed.

**⌘B**, or **⌘-click**, on a module's path opens its `go.mod`: the copy in the module cache for the
version on the line, the folder of a `replace`, or the module's folder when a `go.work` uses it. The
same works on a `use` folder and on a local `replace` path. A module that is not downloaded yet says
so.

Private modules (those `GOPRIVATE`, `GONOPROXY` or `GONOSUMDB` name, such as your company's GitLab)
and replaced modules (by a folder or by another module) are never asked about. Answers are kept for
an hour (and between runs), so the services are asked again only after that; without the network
nothing is shown and nothing fails. Both checks can be turned off in **Settings → Languages &
Frameworks → Go → Dependencies**; with **Check for newer versions of dependencies** off, GoGarden
asks neither the proxy nor `go.dev`, and runs `go`'s own checks with `GOPROXY=off`. The decisions
and what is contacted are in
ADR-0059 and ADR-0066 (`docs/adr` in the repository).
