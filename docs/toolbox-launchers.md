# Zen IDE shell launchers

> **Last updated:** 2026-10-21 · **Decisions:** [ADR-0008](adr/0008-toolbox-and-updates.md),
> [ADR-0043](adr/0043-toolbox-settings-and-shell-launchers.md),
> [ADR-0086](adr/0086-ide-commands-on-path.md) · **Settings:** [toolbox-settings.md](toolbox-settings.md)

Zen Toolbox writes a small script for every installed IDE, and one for zen-cli, into a folder of
the user's choice, so that they start from a terminal by name: `gogarden .` opens the current
folder in GoGarden. Each IDE can write its own from Tools → Create Command-line Launcher….
The scripts and the `PATH` line are `zen_update::scripts`; Zen Toolbox's side is
`zen_toolbox::launchers`, the IDE's `zen_workbench::launcher`.

## Names

A launcher is named by the product id, which is also the IDE's executable (docs/naming.md):
`gogarden`, `rustronin`, `pypetal`, ..., `testtotami`. Each tool in `toolbox.tools.list` carries
its name as `launcher`. zen-cli's launcher is `zen`.

Before ADR-0086 launchers were named by the image part of the product name (`garden`, `ronin`,
`petal`, `wave`, `crane`, `shuriken`, `pagoda`, `ryokan`, `scroll`, `daruma`,
`totami`). Zen Toolbox deletes its own launchers of those names (marked files only) whenever it
generates or removes launchers.

## What a launcher contains

On macOS, Linux and other Unix systems a launcher is a shell script without an extension, mode
`0755`:

```sh
#!/bin/sh
# Generated by Zen Toolbox. Do not edit.
exec "/Applications/GoGarden.app/Contents/MacOS/gogarden" "$@"
```

On Windows it is a batch file, `gogarden.cmd`:

```bat
@echo off
REM Generated by Zen Toolbox. Do not edit.
"C:\Users\me\AppData\Local\Zen Toolbox\tools\gogarden\0.9.0\bin\gogarden.exe" %*
```

- The path is the active version's executable. On macOS it is the executable inside the
  application bundle in the Applications folder (`Contents/MacOS/<id>`, ADR-0025), not `open`,
  so that the arguments reach the IDE: `gogarden --headless .`, `gogarden mcp --headless .`,
  `gogarden main.go:12` (the IDE opens the file at that line, `:12:5` at a column too). With the
  IDE already running on the same data folder, the launcher's start hands the folders and files to
  it and returns at once ([ADR-0111](adr/0111-hand-files-to-the-running-ide.md)). With `--wait` the
  start stays until the tabs of its files are closed, starting the IDE if it does not run, so that
  `git config --global core.editor "gogarden --wait"` edits commit messages in the IDE
  ([ADR-0265](adr/0265-versions-updates-notifications-and-waiting-launchers.md)).
- `zen` starts the zen-cli that an IDE ships: `Contents/MacOS/zen` in its bundle (`bin/zen` next
  to `bin/<id>` outside one), from the first installed IDE in catalog order that has it.
  `cargo xtask release` builds zen-cli and copies it there.
- In the shell script the path is in double quotes, with `"`, `\`, `$` and `` ` `` escaped; in
  the batch file `%` is doubled.
- A launcher is written to a new hidden file next to it (`.<name>.zen-partial`, created afresh
  and never opened through a symbolic link) and renamed into place. The folder is created only
  when there is a launcher to write.
- A tool installed in an earlier tools location (`toolbox.tools.previousLocations`) gets its
  launcher too; when a tool is in several locations, the first one searched wins, as for launching.

## Never touching other files

The second line, `# Generated by Zen Toolbox. Do not edit.` (`REM ...` in a batch file), is the
marker; an IDE's own launcher carries it too. Zen replaces or deletes a file only if it is a
regular file and a line of its first kilobyte is exactly that comment. A file with a launcher's
name that has no marker, a symbolic link (even to a launcher) or a directory is left as it is and
reported as skipped. Files with other names are never looked at.

## Putting the folder on PATH

A launcher can be typed as a command only when its folder is on the `PATH` of the terminal.
Whether it is, is asked of the user's login shell (`$SHELL -i -l -c`, the way a new terminal
window starts, with a five-second limit), and of the running process's own `PATH`.

When it is not, the line that puts it there is, for a folder in the home folder:

```sh
export PATH="$HOME/.local/bin:$PATH"
```

and the folder's full path otherwise. Zen adds it, after the comment
`# Zen IDE command-line launchers (added by Zen Toolbox)`, to `~/.zprofile` (created if missing)
and to `~/.bash_profile` if it exists, unless the file has the line already. **Only on the user's
consent:** the Add to PATH button of Zen Toolbox's Settings page, the ticked checkbox of the IDE's
dialog, or an agent's explicit `toolbox.shellScripts.addToPath` or
`tools.commandLineLauncher.create` with `"addToPath": true`. Nothing else edits a shell file, but
for the completions line below, which has a consent of its own.

## Shell completions

`zen completions <zsh|bash|fish>` prints a completion script. The scripts are small and hold no
data: at every Tab they run the hidden `zen __complete <shell> -- <words>`, so that the candidates
always come from the `zen` that answers, built from its command-line definition and its command
registry ([ADR-0265](adr/0265-versions-updates-notifications-and-waiting-launchers.md)):
subcommands, options, command ids for `zen run`, a JSON skeleton of a command's parameters for
`--params`, the shells for `completions`, product ids for `--ide`. No candidates means the shell
offers files.

`toolbox.shellScripts.generate`, and everything that keeps the launchers current, writes the
scripts too: they exist while the `zen` launcher does. The files carry the
launchers' marker, so one Zen did not write is left alone and reported as skipped:

| Shell | File | Loaded by |
|---|---|---|
| zsh | `~/.local/share/zsh/site-functions/_zen` | the `fpath` line below |
| bash | `~/.local/share/bash-completion/completions/zen` | bash-completion 2, or the line below |
| fish | `~/.config/fish/completions/zen.fish`, only when `~/.config/fish` exists | fish itself |

`toolbox.shellScripts.addCompletions`, the **Turn on completions** button of Zen Toolbox's Settings
page, adds after the comment `# Zen IDE shell completions (added by Zen Toolbox)` one line to
`~/.zprofile` and, if it exists, one to `~/.bash_profile`, on the user's consent only as for `PATH`:

```sh
fpath=("$HOME/.local/share/zsh/site-functions" $fpath)
[ -r "$HOME/.local/share/bash-completion/completions/zen" ] && . "$HOME/.local/share/bash-completion/completions/zen"
```

zsh completes only where `compinit` runs, usually in `~/.zshrc`, which comes after `~/.zprofile`.
Windows gets no completions.

## Zen Toolbox commands

| Command | Parameters | Result |
|---|---|---|
| `toolbox.shellScripts.generate` | `{ "location"?: path }` | a report |
| `toolbox.shellScripts.remove` | `{ "location"?: path }` | a report |
| `toolbox.shellScripts.status` | `{ "location"?: path }` | the launchers there and the `PATH` status |
| `toolbox.shellScripts.addToPath` | `{ "location"?: path }` | `{ "line", "changed": [paths] }` |
| `toolbox.shellScripts.addCompletions` | none | `{ "changed": [paths] }` |

`generate` writes a launcher for every installed tool and `zen`, and deletes the marked launchers
of tools that are not installed and of the old names. `remove` deletes every marked launcher.
`location` is an absolute path or starts with `~`, the home folder; a relative path or an unknown
parameter fails the command. Without `location` the commands use the
`toolbox.shellScripts.location` setting, `~/.local/bin` by default.

The report of `generate` and `remove`:

```json
{
  "location": "/Users/me/.local/bin",
  "written": ["/Users/me/.local/bin/gogarden", "/Users/me/.local/bin/zen"],
  "removed": ["/Users/me/.local/bin/garden"],
  "skipped": [],
  "onPath": false
}
```

`onPath` there is this process's `PATH` only. `status` asks a new terminal window too:

```json
{
  "enabled": true,
  "location": "/Users/me/.local/bin",
  "launchers": ["/Users/me/.local/bin/gogarden", "/Users/me/.local/bin/zen"],
  "onPath": false,
  "inProfile": false,
  "line": "export PATH=\"$HOME/.local/bin:$PATH\"",
  "profiles": ["/Users/me/.zprofile"]
}
```

## The Settings page

The gear menu's **Settings…** opens a page in place of the tool list (`zen-toolbox --settings`
opens on it): **Generate shell scripts** (`toolbox.shellScripts.enabled`), **Shell scripts
location** (`~` allowed; Apply or ⏎), the launchers in the folder, and whether a terminal finds
them: on `PATH`; added to the profile, so new terminal windows will; or not, with the line in a
box and **Add to PATH**. The code is `crates/platform/ui/src/toolbox/settings.rs`.

## Keeping launchers up to date

The settings `toolbox.shellScripts.enabled` (default `true`) and `toolbox.shellScripts.location`
(default `~/.local/bin`) control it ([toolbox-settings.md](toolbox-settings.md)). They are applied
at start-up and on every `toolbox.settings.set`; the code is `Tools::set_shell_scripts` and
`Tools::reconfigure`.

- **On:** Toolbox generates the launchers into the location at once, again at every start, and
  after every install, update and uninstall.
- **A new location while on:** the marked launchers are removed from the old location and
  generated in the new one.
- **Off:** the marked launchers are removed from the location.
- **No location given:** a Toolbox set up without a location (tests, the demo) keeps no launchers,
  so that it never writes into the user's real `~/.local/bin`.
- **`--tools-dir`:** a run with a tools directory on the command line never generates or removes
  launchers on its own. The commands still work.

A failure is shown as a notice (`toolbox-shell-scripts-failed`); the setting is saved anyway.

## In an IDE

Tools → Create Command-line Launcher… (`view.commandLineLauncher.open`)
opens "Create Launcher Script": the name (the product id) and the folder (`~/.local/bin`), whether
a terminal finds that folder, and when it does not the line with the checkbox "Add this line to
~/.zprofile", unticked. OK runs:

| Command | Parameters | Result |
|---|---|---|
| `tools.commandLineLauncher.status` | `{ "folder"?: path, "name"?: string }` | `{ script, exists, onPath, inProfile, line, profiles, changed: [] }` |
| `tools.commandLineLauncher.create` | `{ "folder"?: path, "name"?: string, "addToPath"?: bool }` | the same, with the profiles changed |

The script starts the running IDE's own executable. A file of that name that Zen did not write is
refused, not replaced.

Settings → Tools → MCP Server shows `claude mcp add … -- gogarden mcp` with the short name when
a terminal finds Zen's `gogarden` launcher (checked in the background, again every half minute
while the dialog is open), and with the executable's full path otherwise.
