# ADR-0043: Zen Toolbox settings and shell launchers

- **Status:** Proposed
- **Date:** 2026-10-17

## Context

Zen Toolbox had no settings of its own beyond the interface language and the version whose
"What's new" was shown, both kept in `settings.json` in the user's application data. The requirement:
settings for Zen Toolbox itself: where tools are installed, the release channel, how updates are
checked and applied, shell scripts that launch the tools, and the appearance.
ADR-0008 promised shell launchers (`ronin`, `garden`, ...).

The forces: the settings become a documented file format and public behaviour that AI agents
reach through commands (ADR-0007, ADR-0033); the command line already had `--channel` and
`--tools-dir`; AGENTS.md rule 10 forbids network access that is not explicit and cannot be turned
off; and a generator that writes into a directory on `PATH`, such as `~/.local/bin`, must never
destroy a file that someone else put there.

## Decision

1. **The file.** The settings are flat dotted keys in the existing `settings.json`, read with
   defaults by `zen_toolbox::ToolboxSettings`: `toolbox.tools.location`,
   `toolbox.tools.previousLocations` (kept by Toolbox), `toolbox.channel`, `toolbox.updates.check`,
   `toolbox.updates.tools`, `toolbox.updates.self`, `toolbox.shellScripts.enabled`,
   `toolbox.shellScripts.location`, `ui.theme` and `ui.language`. A missing, mistyped or invalid
   value reads as its default; paths must be absolute. The keys, types and defaults are listed in
   [toolbox-settings.md](../toolbox-settings.md); a change to them needs a new ADR.
2. **Commands.** `toolbox.settings.get` returns every setting with defaults filled in;
   `toolbox.settings.set` takes any subset, validates all of it first with localised messages
   (ADR-0024), rejects unknown fields, writes nothing when anything is invalid, and applies the
   result to the running Toolbox.
3. **Precedence.** For one run the command line wins and is never saved: `--channel` over
   `toolbox.channel`, `--tools-dir` over `toolbox.tools.location` (and it is then the only tools
   directory searched), `--releases none` over `toolbox.updates.check`. A saved setting that a flag
   overrides takes effect at the next start without the flag.
4. **Tools location.** A new location applies to new installations only. Installed tools are not
   moved; their directories are remembered in `toolbox.tools.previousLocations`, newest first, and
   searched after the current location, so tools there keep launching, updating and uninstalling
   where they are. Choosing a remembered location again takes it off the list.
5. **Checks and the network.** `toolbox.updates.check = manual` means Zen Toolbox makes no network
   request at all until the user asks (**Check for Updates**, `toolbox.releases.refresh`); the
   window says that releases are not checked yet. `automatic` keeps the earlier behaviour (at
   start, on opening the window and every 30 minutes). No new setting contacts the network by
   default: every new default either keeps the earlier behaviour or does nothing.
6. **Automatic updates.** `toolbox.updates.self = automatic` downloads and installs a newer Zen
   Toolbox in the background after a check finds it, with the same signed-manifest verification as
   a manual update; the restart stays the user's. `toolbox.updates.tools = automatic` is stored but
   behaves as `notify` until Toolbox can tell whether a tool is running. Both default to `notify`.
7. **Shell launchers.** `toolbox.shellScripts.generate` and `toolbox.shellScripts.remove` write and
   delete one launcher per tool, named by the image part of the product name, in a location that
   defaults to `toolbox.shellScripts.location`. With `toolbox.shellScripts.enabled` (default
   `false`) Toolbox keeps them current: at start-up, when the setting is turned on or the location
   changes, and after every install, update and uninstall; turning it off, or moving the location,
   removes the launchers it wrote. A run with `--tools-dir` never does this on its own.
8. **The marker rule.** Every launcher carries the line `# Generated by Zen Toolbox. Do not edit.`
   (`REM ...` in a batch file). Zen Toolbox replaces or deletes a file only if it is a regular file
   with that exact line in its first kilobyte. Anything else with a launcher's name, including a
   symbolic link, is reported as skipped and left alone; files with other names are never looked at.
   Launchers are written to a freshly created temporary file and renamed into place.

## Consequences

- Settings are reachable by AI agents and by a future settings page through the same two commands.
- Removing launchers when the setting is turned off is safe only because of the marker rule; any
  future change to the launcher format must keep a marker that the old rule recognises.
- `toolbox.tools.previousLocations` can collect locations that no longer hold tools; they cost one
  directory lookup each.
- `ui.theme` is stored only until the light theme can be applied at run time.
- Five launcher names (`crane`, `shuriken`, `pagoda`, `ryokan`, `scroll`) are provisional
  until docs/naming.md lists them.

## Alternatives considered

- **A separate Toolbox settings file or a nested format:** a second file and a migration for no
  gain; the flat keys of `zen_core::Settings` already serve the IDEs.
- **Moving installed tools to a new location:** slow, can fail half way and breaks running IDEs;
  remembering old locations is simpler and safe.
- **One channel per tool:** more settings for a case nobody asked for yet.
- **Leaving launchers in place when the setting is turned off:** stale launchers would keep
  pointing at old versions; marker-checked removal makes the switch mean what it says.
- **Symbolic links instead of scripts:** they cannot carry a marker, do not work the same on
  Windows, and would hide whether Zen Toolbox owns a file.
