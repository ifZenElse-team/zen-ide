# ADR-0020: The release server stores, the publisher signs

- **Status:** Accepted
- **Date:** 2026-10-16
- **Refines:** [ADR-0008](0008-toolbox-and-updates.md) (decision 3), [ADR-0017](0017-project-domain.md) (decision 3)

## Context

Zen Toolbox installs and updates tools from a signed release manifest (ADR-0008). Something has to
host the manifest and the release artifacts, accept new releases, and never let a compromised host
or a stolen credential push a build that users would trust.

## Decision

1. **`zen-update`** (L5) defines the release manifest (schema version 1, JSON), signs and verifies it
   with ed25519, and selects the newest release of a product for a channel and platform. Zen Toolbox,
   the release server and the publishing tool all use it, so there is one definition of the format.
   The format is documented in `docs/release-manifest.md`.
2. **The manifest is signed over its exact bytes.** The signature is stored next to it
   (`manifest.json.sig`, hex). Clients verify before parsing; nothing in an unverified manifest is
   used. Artifacts are referenced by URL relative to the manifest, with their SHA-256 and size, and
   clients verify the hash before unpacking.
3. **`apps/zen-releases`** is one binary with three commands:
   - `serve`: an HTTP server (axum) that serves `/releases/manifest.json`, its signature and
     `/releases/artifacts/...` from a data directory, and accepts uploads on `/api/v1/` with a bearer
     token;
   - `keygen`: creates a signing key pair;
   - `publish`: uploads an artifact, adds it to the current manifest, signs the new manifest with
     the publisher's secret key, and uploads it.
4. **The server never holds the signing key.** It knows only the trusted public key and rejects a
   manifest whose signature does not verify, or that references an artifact it does not have with
   the stated hash and size. A stolen upload token can therefore not publish a build users would
   accept.
5. **TLS is terminated in front of the server** (for example by Caddy, as in the team's other
   deployments). The server speaks plain HTTP and binds to loopback by default.
6. **During development everything is local** (ADR-0015, decision 3): the server runs on
   `127.0.0.1`, with a development key pair generated by `keygen` that is never used for public
   releases, and Toolbox is pointed at it explicitly.

## Consequences

- The production signing key lives with the release maintainer or in the release pipeline, with a
  custody procedure written before the first public release.
- Toolbox downloads over plain HTTP during development. **Open question:** the HTTPS client for
  production. Common TLS stacks (`ring`, `aws-lc-rs`) contain C and assembly, which ADR-0002 keeps out
  of the default build; the choice (a pure-Rust provider, or an ADR-backed exception) is due before
  the first public release.
- The data directory is the whole state of the server: backing it up backs up every release.

## Alternatives considered

- **A static host only (no server):** simplest to run, but publishing would need host-specific
  tooling, and nothing would check a manifest's signature on upload.
- **The server signs manifests:** convenient, but a compromised server could sign anything.
